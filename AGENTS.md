# MMS Agent Guide

This repository is an **npm workspaces** monorepo. The Remix app lives in `apps/web`; the root scripts delegate to it.

## Commands

```sh
npm i
npm run dev
npm run hmr
npm run start
npm test
npm run typecheck
npm run check
npm run doctor

npm run db:bootstrap   # roles, schemas, extensions (idempotent)
npm run db:check       # lint + C1/C3/C5 on fresh databases
npm run db:spike       # pgschema object-coverage spike suite
npm run db:test        # pgTAP tests against $DATABASE_URL
npm run db:verify      # C5 + pgTAP against a running database
npm run db:plan -- --name <name>   # generate a reviewed migration
npm run db:migrate     # apply pending migrations
npm run db:reset -- --force        # rebuild the database from scratch
npm run db:dump        # schema-only dump for inspection
npm run db:fixtures    # development organisation fixtures
```

Use `npm run hmr` for live server and browser updates; `npm run dev` only watches and restarts the server. `npm run start` runs in production mode without a separate build step. `npm run check` runs the workspace typecheck and tests. `npm run doctor` runs `remix doctor` in `apps/web`. The web workspace test script uses `remix test --concurrency 1`: these suites are integration tests sharing one PostgreSQL database (`audit_trail.seal`, `iam.login_attempt`), so parallel files race. Keep the flag when bumping `@remix-run/test`.

## Layout

- `apps/web/` — the only deployable workspace. `apps/web/app/` is the Remix app; `apps/web/server.ts` and `apps/web/hmr.ts` are the runtime entries; `apps/web/public/` holds static files.
- `packages/` — framework-agnostic libraries (`domain`, `pgrst-client`, `test-utils` as they are added).
- `db/` — declarative schema, bootstrap, migrations, seeds and database scripts (not a workspace).
- `infra/` — local compose and deployment assets (not a workspace).
- `docs/` — ADRs, architecture, unified implementation plans (`docs/plans/README.md`), security notes, domain and compliance docs (see `docs/README.md`).

## Remix Conventions

Refer to `./.agents/skills/remix/SKILL.md` for the Remix mental model and how to find guides and API READMEs through `node_modules/remix/INDEX.md`.

- `apps/web/app/routes.ts` defines the shared route contract used by server and browser modules for type-safe hrefs.
- `apps/web/app/router.ts` wires routes to controllers and installs the standard Remix component renderer used by actions.
- With nested routes, each group maps to its own controller directory: `apps/web/app/actions/<route-key>/controller.tsx` serves the direct leaves of `routes.<route-key>`; the root controller at `apps/web/app/actions/controller.tsx` serves only `/assets` and `/.well-known/jwks.json`. Group names are the route map keys (e.g. `mfa`, `uploads`); directory names must be kebab-case per remix doctor.
- `apps/web/app/assets.ts` owns the server-side asset pipeline used by the asset route and render middleware.
- Browser-reachable modules are public. Keep secrets and trusted server logic out of `public/` directories and out of modules imported by browser entries.
- Run `remix doctor` after structural or configuration changes.

## Database Changes

- `db/src/` is the declarative desired schema, one folder per schema.
- `pgschema` diffs the desired state and produces reviewed migration directories under `db/migrations/`; never hand-edit a merged migration.
- Production applies only reviewed migrations through the project runner. pgschema is a diff generator and drift detector, not an approval mechanism.
- The migration checks C1–C8 and the schema lint are part of the gate. See the implementation plan for the exact checks.
- Schema changes that affect grants, policies, `SECURITY DEFINER` functions, the `auth` schema, authority rules or the token signer need the `security-review` label and two reviewers.
- Never compare `session_user` or `current_user` inside a function body: inside a `SECURITY DEFINER` function both report the definer, so such a guard never denies anyone. Use `private.is_worker()` / `private.caller_role()`; the schema lint rejects the tokens (ADR-0017).
- **Never use `serial`, `bigserial`, or `smallserial`** ("Where to use identity instead"). Use SQL-standard identity columns: `generated always as identity` (or `generated by default as identity`) for auto-incrementing integer/bigint surrogate keys. Legacy `serial` creates decoupled external sequences, causes permission drift, and risks out-of-sync sequence errors on manual inserts. Enforced by schema lint (`npm run db:check`) and ADR-0034. Primary domain entities continue to use UUIDv7 (`id uuid default uuidv7() primary key`).

### Production Baseline & Migration Immutability (`FIRST_PRODUCTION_BASELINE`)

**Status: NOT_ESTABLISHED (Pre-Production Prototype Normalization Complete)**

MMS is in pre-production prototype development. The schema architecture has undergone clean historical normalization:
1. **Technical Audit Trail (`audit_trail`):** All 84 prototype migrations (`20261030T111331Z_f04-poc` through `20261108T085334Z_r8-5-closure`) consistently define and target `audit_trail` for technical audit operations (change logging, security events, cryptographic sealing, reconciliation, WORM).
2. **Maritime Company Audit Reservation (`audit`):** The `audit` namespace is strictly reserved for the future maritime Company Audit domain (`audit.programme`, `audit.job`, `audit.report`, `audit.finding`, etc.).
3. **Baseline Preview:** The authoritative preview of the normalized 84-migration baseline is verified and maintained at `docs/review/production-baseline-preview.lock.json`.
4. **Transition to Permanent Immutability:** Once MMS is ready for production release, the formal baseline freeze is executed via the approved release workflow (`.github/workflows/baseline-freeze.yml`) targeting protected GitHub Environment `production-release` with required reviewers and annotated release tag verification. That operation is strictly one-way and irreversible: it verifies complete lock coverage, enforces a clean working tree and full gate replay, writes `db/production-baseline.lock.json`, and permanently locks migrations 1–84 against alteration or deletion in CI. All subsequent database schema changes must be forward-only migrations starting from migration 85. Until that formal transition, `FIRST_PRODUCTION_BASELINE = NOT_ESTABLISHED`.

## Working Rules

- **No backward compatibility:** Delete obsolete things directly—don't add compatibility layers, don't write migration scripts, and don't keep fallback plans.
- **Simplicity first (YAGNI):** Choose the simplest implementation that meets current needs. Don't build preventive abstractions, and don't add configuration layers for "just in case we need them later."
- **Layered growth:** The system should grow in layers. First get a minimal end-to-end version working; once it runs, add things on top. Absolutely do not tear down something that currently works just because of complexity that might arise in the future.
- **Modularity:** Keep components modular, with clear separation of concerns.
- **Mature dependencies:** Prefer mature, maintained third-party libraries. Unless there's a particularly strong reason, don't rewrite them yourself.
- **Leverage existing dependencies:** Before starting, first check what the project's existing dependencies can do, then decide whether to add a new package or write it yourself. Don't assume the library definitely doesn't have it.
- **Long-term architectural decisions:** Make architecture decisions with the long term in mind. Don't accept temporary solutions like "just make it work for now, we'll deal with it later."
- **Proven patterns:** First look at how mature products solve the same problem, and use proven patterns—don't invent from scratch.
- **Focused scope:** Build only what the current task card needs.
- **Conventions & ADRs:** Do not invent conventions. If something is missing, add a proposed ADR and stop for human review.
- **Preserve baseline conventions:** Preserve npm, the workspace layout, middleware order and import conventions unless the task requires changing them.
