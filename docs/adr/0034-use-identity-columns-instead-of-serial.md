# ADR-0034: Use SQL-Standard Identity Columns Instead of Legacy Serial

- Status: accepted
- Date: 2026-11-22
- Context: PostgreSQL Community Best Practices ("Don't Do This: Don't use serial" / "Where to use identity instead")
- Related: ADR-0005 (principal identity), ADR-0010 (pgschema), ADR-0028 (canonical party and vessel identity)

## Context

PostgreSQL historical pseudo-types `serial`, `bigserial`, and `smallserial` are non-standard shorthand macros that:
1. Implicitly create an external sequence (`<tablename>_<colname>_seq`).
2. Attach a default expression (`DEFAULT nextval('...')`).
3. Associate ownership via `OWNED BY`.

This legacy approach introduces several operational and security hazards:
- **Permission and Privilege Drift:** Inserting into a table with a `serial` column requires separate `USAGE` privileges on the underlying sequence in addition to `INSERT` on the table.
- **Out-of-Sync Sequences:** Manually inserting an explicit value into a `serial` column does not advance the sequence counter, causing subsequent default inserts to fail with duplicate key violations.
- **Copying Table Trap:** Duplicating a table definition with `CREATE TABLE ... (LIKE ... INCLUDING DEFAULTS)` copies the exact default expression, causing the new table to inadvertently draw values from the old table's sequence.
- **Non-Standard SQL:** `serial` is proprietary PostgreSQL syntax not aligned with the ISO SQL standard.

The official PostgreSQL Wiki guidance (*"Don't Do This: Don't use serial"*, section *"Where to use identity instead"*) specifies that for PostgreSQL 10 and newer, standard SQL identity columns (`GENERATED ALWAYS AS IDENTITY` or `GENERATED BY DEFAULT AS IDENTITY`) must be used instead.

While MMS uses UUIDv7 (`id uuid default uuidv7() primary key`) for primary domain entities, certain internal catalogues, breakdown nodes, and audit tables utilize integer/bigint surrogate keys. Previous prototypes introduced `serial` columns in `core` and `fleet` schemas, diverging from the SQL-standard identity pattern already established in `audit_trail.change_log` and `iam.login_attempt`.

## Decision

1. **Mandate SQL-Standard Identity Columns:**
   Surrogate integer or bigint primary keys in MMS must use SQL-standard identity column syntax:
   ```sql
   id integer generated always as identity primary key
   -- or for 64-bit integer keys:
   id bigint generated always as identity primary key
   ```
   Where explicit fixture or migration IDs must be accepted without `OVERRIDING SYSTEM VALUE`, `GENERATED BY DEFAULT AS IDENTITY` may be used.

2. **Prohibit `serial` Pseudo-Types:**
   The pseudo-types `serial`, `bigserial`, and `smallserial` are strictly forbidden across all `.sql` files in `db/src/`.

3. **Schema Lint & CI Enforcement:**
   `db/scripts/lint-schema.ts` includes an automated check rejecting any occurrence of `serial`, `bigserial`, or `smallserial` in `db/src/`. Schema checks run during `npm run db:check` and as part of the release gate (`npm run release:check`).

4. **Agent Guidelines:**
   Repository guidelines in `AGENTS.md` explicitly instruct all current and future autonomous agents to adhere to this convention under the section *"Identity Columns vs. Serial ('Where to use identity instead')"*.

## Consequences

- All surrogate integer keys now adhere to ISO SQL standard syntax.
- Sequence privileges are encapsulated directly within table column permissions.
- Out-of-sync sequence errors are eliminated.
- Automated lint prevents regressions across both human and agent contributions.
